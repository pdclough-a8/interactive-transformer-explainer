# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository overview

This repo contains a single, self-contained HTML file:

- `index.html` - an interactive, client-side explainer ("How a transformer works") built for Analytics8. It walks through tokenization → embeddings → positional encoding → attention → multi-head attention → transformer blocks → depth/stacking → next-token generation → a toy training demo → post-training (predictor to assistant) → RAG/tools/agents. Named `index.html` (rather than something more descriptive) specifically so GitHub Pages serves it directly at the site root with no redirect stub needed - don't rename it or reintroduce a second copy of this file (that previously caused the live site to go stale - see git history around "resync index.html").

There is no build system, package manager, bundler, or test suite. This directory **is** a git repo (remote: `origin` → GitHub) and pushes to `main` auto-deploy to GitHub Pages via `.github/workflows/static.yml` - so a push, not just a local save, is what makes a change visible on the live site. The page can also be opened directly in a browser (double-click, or via a simple static file server) for local testing.

`README.md` is the human-facing project description (what the page covers, the three view toggles, what's real vs. illustrative, design philosophy). Keep it in sync with `index.html` at a high level, but it doesn't need updating for every small content tweak - this file (`CLAUDE.md`) is the one that needs to track structural/code changes closely.

## Running / testing

There are no build or test commands. To view changes:

- Open `index.html` directly in a browser, or serve the directory with any static file server (e.g. `python -m http.server`) if `file://` restrictions cause issues with the ES module script (see Tokenizer below).
- There is no linter or formatter configured. Match the existing minified/dense inline style (CSS and JS are extremely compact, single-line-per-rule) when editing.
- After any JS edit, it's worth a quick sanity check that the inline `<script>` blocks still parse, since there's no build step to catch a syntax error before it ships:
  ```
  node -e "const fs=require('fs');const html=fs.readFileSync('index.html','utf8');[...html.matchAll(/<script(?![^>]*type=\"module\")[^>]*>([\s\S]*?)<\/script>/g)].forEach((m,i)=>{try{new Function(m[1])}catch(e){console.log('ERROR',i,e.message)}})"
  ```
- Since this is a pure front-end demo with no automated tests, also verify changes manually in a browser: type a sentence into the input, and click through each numbered station (tokens, embed, position, attention, heads, block, depth, output, assistant, beyond) in both Plain English/Technical layer states and both Using it/Teaching it modes to confirm rendering still works and nothing throws in the console.

## Structure of the single HTML file

Everything lives in one file, organized top-to-bottom as:

1. **`<style>`** (head) - all CSS, using CSS custom properties (`:root { --ink, --orange, --blue, ... }`) for the Analytics8 brand palette/fonts. Class names are short/dense (e.g. `.qkv-grid`, `.heat`, `.mat-cell`, `.stackviz`, `.arch-row`, `.ffn-diagram`).
2. **`<body>`** - markup for:
   - Top bar + hero with the sentence input, example buttons, and an inference/training mode toggle (`#m-infer` / `#m-train`, toggles `body.mode-training` / `body.mode-inference` CSS classes which show/hide `.only-train`/`.only-infer` blocks).
   - A "Plain English" vs "Add the technical layer" toggle (`#t-plain` / `#t-tech`, toggles `body.show-tech` to reveal `.tech-block` elements and any `.only-tech`-wrapped content) - every station has a plain-language explanation plus an optional technical/detail aside. Technical-layer prose deliberately avoids bare mathematical notation where the same idea can be said in plain sentences without losing anything useful - formulas are the exception, not the default, and are trimmed on sight unless they're genuinely illuminating (e.g. a fully worked, narrated numeric example).
   - A left-hand sticky nav rail (`nav.rail`) linking to each `section.station` (ids: `overview`, `tokens`, `embed`, `position`, `attention`, `heads`, `block`, `depth`, `output`, `assistant`, `beyond`, `bigideas`, `history`, `resources`).
   - Each `section.station` is one stage of the pipeline, containing one or more `.demo` panels (mostly `<details class="demo">` with a `<summary class="demo-lab">`, collapsed by default) with the interactive visualization for that stage (canvas-drawn maps/heatmaps, DOM-built token chips, sliders, tabs, inline SVG diagrams, etc). Several stations also carry a small `<details class="qpop">` box linking to curated external resources (TensorFlow Projector, Embedding Atlas, Transformer Explainer, exBERT, the original RAG paper, Anthropic's "Building Effective Agents", etc.) - keep these to genuinely high-quality, non-vendor-sales-page sources.
3. **Data blobs** (`<script>` before the module script) - `window.__BPE__` (offline BPE merges/vocab trained on a small corpus) and `window.__EMB__` (hand-curated 2D word-embedding map with categories/neighbours/palette, used for the embeddings visualization and the king−man+woman analogy demo).
4. **`<script type="module">`** - loads the real `cl100k_base` tokenizer from `https://esm.sh/gpt-tokenizer@2.9.0` (requires network access / non-`file://` context in some browsers) and exposes it as `window.__cl100k__`. Dispatches a `tokenizer-ready` event.
5. **Main `<script>` IIFE** - all interactive logic, `"use strict"`, no external dependencies beyond the tokenizer module. Key pieces:
   - **Tokenizer**: `tokenize()` tries the live `cl100k` encoder first (`TOKMODE==="live"`), falling back to the offline hand-rolled `bpeEncode()` BPE implementation (`TOKMODE==="offline"`) if the module import fails (e.g. no network / opened via `file://`). This is the one part of the pipeline that's genuinely real end to end - everything described below is an illustrative approximation.
   - **Toy embeddings**: `embed(text)` is a deterministic hash-based pseudo-embedding (16 dims, seeded PRNG) - illustrative only, not a real trained embedding.
   - **Position encoding**: `posEnc(p)` implements the standard sinusoidal formula for visualization. `renderPosHeat()` draws one row per position in the *current* sentence (capped at `MAX`) and must be called from `rerender()` - it used to be hardcoded to a fixed 10 rows and rendered once at load, which meant it silently never updated; keep it wired into `rerender()`.
   - **Attention simulation**: `computeAttn(mode)` fabricates plausible attention-weight patterns (not real learned attention) via cosine similarity of the toy embeddings, a recency term, and `pronounBoost()` (a hardcoded rule: personal pronouns - she/he/they/etc. - get boosted toward a hand-listed `PERSON_WORDS` set; impersonal pronouns - it/this/that/etc. - are explicitly excluded from person words and boosted toward other content words instead). `mode===undefined` is the main single-head pattern; modes `0/1/2` are three canned "head personalities" used in the Many Heads station: previous-token, semantic-similarity, and pronoun-reference (this last one was originally an "attention sink" head, but was swapped out because it didn't match the "grammar / references / previous token" categories the station's own lead-in promises, and reuses `pronounBoost()`). `computeAttnUnmasked()` is the same scoring with the causal restriction removed, used by the "turn off the causal mask" toggle (`S.maskOff`) in the Attention station - it must stay a *separate* function/path from the main masked matrix, since the live "who's attending to whom" arc diagram (`renderAttnArcs`) should always reflect the real causal mechanism regardless of that toggle's state.
   - **Rendering functions**: one `render*` function per station (`renderTokens`, `drawMap`/`findNeighbours`/`showAnalogy` for embeddings, `renderPosHeat`/`renderPosSum`, `renderHeat`/`renderFocus`/`renderAttnHeat`/`renderAttnArcs` for attention, `renderHeads`, `renderStack` for the depth/layer stack, `renderMatrix`/`renderSizes` for the "matrix size" panel).
   - **Toy next-token generator** (station 8, inference view): a trigram language model (`TRI`/`BI`/`UNI` counts) built by `buildLM()` from a large hardcoded `CORPUS` string (~480 sentences: ~350 hand-written, spanning many everyday topics - work, weather, food, family, technology, sport, travel, health, shopping, entertainment, animals, and common verb-phrase connectors like "decided to"/"managed to" - plus ~120 sentences extracted verbatim from this page's own prose (lead-ins, analogies, takeaways), specifically so that copying a sentence from the explanation you just read - a very common thing to try - is likely to get decent coverage. It was originally only ~90 sentences concentrated on three scenarios matching the example buttons, which meant most arbitrary user-typed sentences got poor trigram coverage and fell back to generic word frequency. A separate approach - deriving a much larger, broader statistical table offline from a real reference corpus (the Brown Corpus) - was tried and abandoned: even after aggressive pruning it was several times larger in actual gzip transfer size than hand-written sentences, since a real corpus's breadth is genuinely more information, not just an encoding problem. Any fixed corpus will still miss some phrasing no matter its source - that's expected and disclosed via the tier label (plus a live "weak signal" caveat, see `lmWeakSignal` below), not a bug to chase further). `candidatesLM()` scores continuations with trigram→bigram→unigram backoff plus anti-repetition penalties and sentence-ending heuristics, and sets a module-level `lmWeakSignal` flag whenever the current two-word context has no real trigram/bigram support and the demo has fallen back to generic word frequency; `renderProbs()` reads that flag to show/hide a live caveat (`#lm-weak-note`) and applies temperature/softmax for the probability bars; `sampleOnce()`/`resetGen()` drive the "add next word" / "auto-write" / "reset" buttons. If you change the corpus meaningfully, update the "~480 sentences" figures in the station's own tier/note text to match (there are two), and the topic list in the note above the demo if the *hand-written* portion's topics change (the page-prose portion doesn't need its own topic list - it's "the page you're reading").
   - **Toy training demo** (station 8, training view): `trStep()`/`trGuess()`/`drawLoss()` simulate a loss curve and a garbled-to-correct output as "training" progresses - this is a scripted animation, not a real model being trained.
   - **Master state**: a single `S` object (`{toks, ids, embs, attn, head, gen, newN, timer, maskOff}`) holds current sentence state; `rerender()` re-tokenizes/re-embeds/re-renders every station whenever the input sentence changes (debounced via `deb`/`setTimeout`). A few small pieces of UI-only state live as plain top-level `let`s near their own wiring instead of in `S` (e.g. `pronounSwapSaved` for the Attention station's pronoun-swap button) - when adding a render/state hook that other functions need to see, prefer adding to `S` unless it's genuinely local to one demo.
   - **Tooltip system**: `.term` spans with a `data-def` attribute get a shared floating tooltip (`#tip`) wired up at the bottom of the script (hover/focus/click/keyboard accessible), bound both at load and dynamically via `window.__bindTerms` for content injected later (e.g. `renderSizes`). A `.term` span is interactive (`role="button" tabindex="0"`, has its own click handler) - never nest one inside a `<button>` or another interactive element, since that both violates the HTML content model and can cause the two click handlers to fight (this happened once with the mode-toggle button; the fix was to add the tooltip to a nearby plain-text mention instead).

## Editing conventions specific to this file

- CSS and JS favor extreme density (many statements per line, minimal whitespace) - this appears to be an intentional style for this file rather than an accident; follow it for consistency rather than reformatting into a more spread-out style.
- Plain-English copy and technical/detail copy are deliberately kept in separate blocks (`.only-*`, `.tech-block`) so the same station can serve both toggle states - when adding a new station or concept, provide both a plain explanation and a `.tech-block` counterpart gated by `body.show-tech`. Within the technical layer, prefer describing a mechanism in plain sentences over bare formulas/notation unless the notation itself is genuinely illuminating - this was a deliberate, repeated cleanup pass across every station (see git history), not just a one-off preference.
- Elements nested inside a `<button>` must be phrasing content with no interactive descendants (no `<div>`/`<p>`, no nested `.term`) - use `<span>` with `display:block`/`flex` set explicitly where block-level layout is needed, since a `<span>` doesn't default to it the way a `<div>` does.
- Live/computed demos default to collapsed (`<details class="demo"><summary class="demo-lab">...`) rather than always-open, following a pass that converted most of them from plain always-visible `<div class="demo">` panels.
- Every live or illustrative visual carries an explicit realism tag (`.tierline` with 🟢 Real / 🟡 Simplified / 🔵 Illustrative, as introduced in the Overview station's "How to read the demos" primer) - never let a new demo go untagged, and never upgrade a tag's claimed realism without the underlying computation actually changing.
- All "model" data used in visualizations (embeddings map, attention patterns, trigram corpus, BPE vocab) is intentionally toy/illustrative, hand-tuned to produce pedagogically clean results (e.g. the king−man+woman analogy is hand-placed in `__EMB__`, not computed from real embeddings). When adjusting these, preserve the illustrative intent rather than trying to make them "more realistic" at the cost of clarity - the trigram corpus expansion above is the exception, since broadening coverage there directly serves the existing tier label's promise rather than fighting it.
- The GPT-2-small-based numbers in `renderSizes()` (768 dims, 12 layers, 124M params, 50,257 vocab) and the GPT-3/frontier comparisons elsewhere are intentionally fixed reference figures for the "size" explanation - keep these consistent if edited, and keep the existing "frontier numbers vary across vendors" caveat rather than presenting any single frontier figure as exact.
