Training mode - what's actually different

The 8-step forward pass you explored works identically in both modes - switching here doesn't swap it out. What changes is a single step that wraps around it: after the model makes its prediction, training compares it to the true next token, measures the error, and uses that to nudge every weight a tiny bit. Then it does that billions of times. The orange "While training" notes throughout mark exactly the places in the pipeline where that matters. Everything else is running unchanged underneath.

00

The big picture - the whole transformer in one page

Before the details, here's the whole journey. A transformer turns your text into tokens, lets those tokens exchange information and refine each other many times over, then predicts the next word - and repeats. Scaled up and trained on huge amounts of text, that simple loop produces surprisingly rich language ability. Every stage below is one stop on the line. Click a stage to jump to it.

→ → →

↩︎ That last step loops: each new token is fed back in to predict the next. That's the entire generation loop: predict one token, append it, then repeat.

Neural networks? A neural network is a large collection of simple mathematical operations: numbers go in, get multiplied by adjustable numbers called weights, and numbers come out. Training is the process of slowly tuning those weights until the output is useful. A transformer is one particular arrangement of these operations, designed so tokens can exchange information with each other - which turns out to be remarkably good at language.
01

Tokenise - cut the text into pieces

A model can't read words directly. First it segments your text into tokens - usually whole words, sometimes pieces of words or punctuation - and swaps each for an ID number from a fixed dictionary.

🧩Think of it like this: a fixed box of building bricks (around 100,000 of them). Any sentence ever written can be snapped together from those bricks. Rare or invented words just get built from several smaller bricks.
Technical layer

Production models use learned sub-word tokenisers - byte-pair encoding (BPE) / SentencePiece. This tool uses OpenAI's real cl100k_base tokeniser when online, so IDs and splits match GPT-3.5/4. Offline, it falls back to a small BPE we trained ourselves - same algorithm, smaller vocabulary.

Live - your sentence as tokens

Want to try it on your own text? TikTokenizer is a free interactive tokeniser that shows the same splits, live.

While training The tokeniser is built once, up front, from large collections of text - then frozen. Training never changes how text is split; it only changes what the model does with the tokens afterwards.

❓ What about a word it has never seen?

This depends on how the tokeniser was built. Production tokenisers like the one this tool uses are built at the byte level: their base vocabulary is always the 256 possible byte values, with everything else built as merges on top. That means any text - a new brand name, a typo, even a script the tokeniser has never encountered - can always be broken down, worst case into individual bytes. There is no gap to fall through; it may just take many tokens to spell something unfamiliar.

A small tokeniser trained on a narrow dataset - like this tool's own offline fallback - doesn't automatically get that guarantee. If it still keeps individual characters as a base layer, it degrades the same way: unfamiliar words fall back to single letters, which is inefficient but works, since ordinary training text contains every letter. But if its vocabulary is built only from whole words or fragments actually seen in training, with no character-level fallback, then a genuinely new character - one that never appeared anywhere in that training data - has no ID at all. At that point there are only two options, both lossy: substitute a placeholder like an <UNK> token (the old word-level fix), or fail on that input.

Either way, one nuance stays true regardless of tokeniser: being able to spell a word isn't the same as understanding it. If a concept never appeared in training, the model can often still read and write the tokens, but its grasp of the meaning will be weak.

02

Embed - turn tokens into meaning

An ID like 8417 means nothing on its own. So each token is swapped for an embedding: a long list of numbers that acts as the token's coordinates on a map capturing many aspects of meaning and usage. Tokens used alike land close together.

🗺️Think of it like this: every token gets a location on a map - except the map has hundreds of dimensions, not two. Distance means difference in meaning, and directions can carry relationships (the classic word-embedding example: king − man + woman ≈ queen).

From a list to a grid. These per-token vectors stack into a matrix - one row per token, one column per dimension. So your sentence becomes a tall grid of numbers, not a short list. The model's own "knowledge" is likewise huge matrices of weights - running text through a transformer means these grids being multiplied together, layer after layer.

Where do these sizes come from? They're mostly deliberate choices:

The vocabulary size is fixed when the tokeniser is trained - bigger means fewer tokens per sentence, but larger matrices. The width, layers and heads are architecture choices, scaled up for bigger models following scaling laws - observed patterns for how size, data and performance relate. The context window is limited by memory and compute, because attention compares every token with every other - so cost grows with the square of the length.

📏Variable input, fixed output. The context window is a maximum, not a requirement. You can feed the model a single token or fill it to the limit - the transformer handles whatever length you give it, up to that ceiling. During generation, the input starts at the length of your prompt and grows by one token each step. The output, by contrast, is always the same fixed size: a probability score for every single token in the vocabulary - around 100,000 numbers, every time, regardless of how long the input was. That asymmetry is easy to miss: the context window is a cap on what goes in, not a fixed frame that must be filled.

❓ Why 50,257, specifically?

It's not a count of "how many unique words exist" - it's a target size chosen up front, then the tokeniser is trained to fill it. BPE starts from the 256 possible byte values (so anything can always be spelled out, worst case) and repeatedly merges the most frequent adjacent pair in the training corpus into a new token, one merge = one new vocabulary entry. GPT-2's creators simply stopped after 50,000 merges, added the 256 byte tokens and 1 special end-of-text token, and got 256 + 50,000 + 1 = 50,257. GPT-3 and this tool's live tokeniser (cl100k_base) inherit vocabularies from the same lineage of design choices.

So the contents of the vocabulary are data-driven (frequent byte-pairs earn merges), but the size is a human-picked trade-off: bigger vocabulary → shorter token sequences but a larger embedding/output matrix (more weights, more compute per prediction); smaller vocabulary → smaller matrices but longer sequences for the same text.

Technical layer

Every projection is a matrix multiply: a token row 1×d times a weight matrix d×d → 1×d. Attention builds Q, K, V this way; the feed-forward uses d×4d then 4d×d. The embedding / unembedding matrix is V×d - for GPT-3 that's 50,257 × 12,288 ≈ 617 million numbers on its own. Multiply across all layers and you reach the billions.

While training These coordinates start out random - every token dumped in a meaningless heap. Training slowly slides each token into place, so tokens that appear in similar contexts drift together. The map is learned, not designed.

03

Position - keep track of word order

A quirk: the model looks at all tokens at once, not left to right. Without help it couldn't tell “dog bites man” from “man bites dog”. The fix: blend a position signal into each token, so every vector also carries “I'm token #3”.

🎫Think of it like this: numbered tickets at a deli counter. Everyone's visible at once, but each ticket keeps the order straight.
Technical layer

The original paper used fixed sinusoids:

PE(pos,2i)=sin(pos/10000^(2i/d)) · PE(pos,2i+1)=cos(pos/10000^(2i/d))

Each dimension oscillates at its own frequency, giving every position a unique fingerprint. Modern models often use learned positions or rotary embeddings (RoPE).

04

Attention - tokens exchange information

This is the transformer's signature move. For every token the model asks: which other tokens matter for understanding me? - then exchanges information with those tokens, weighted by relevance. That's how “she” can pull meaning from whoever she refers to.

🗣️Think of it like this: a meeting where every token interviews every other. Each asks a question (query), each advertises what it offers (key), and the best matches exchange their content (value). Strong matches get more airtime.

Why three separate roles, not one? Every token needs to do two different jobs at once: ask what it needs from others, and advertise what it offers others. Asking and advertising aren't the same thing, so the model keeps them as separate, smaller vectors - plus a third for the actual content that gets shared once a match is found. That split is what "Query, Key, Value" means:

Query Q
This token's question: “what am I looking for?”
Key K
This token's advert: “here's what I'm about” - checked against everyone's Query.
Value V
This token's actual content - only handed over to whoever's Query matched.

Every token has all three at once - it's simultaneously asking, advertising and ready to share. To score a match, the model compares one token's Query with another's Key using a dot product - a single “how well do these fit?” number. Softmax turns a token's match scores into percentages that add up to 100%, then those percentages are used to blend everyone's Values - a strong match contributes a lot of its Value, a weak one barely any. Splitting the job this way is what makes it efficient: Query and Key exist purely to find relevance; Value is only pulled in for whoever's actually relevant.

❓ Want to see the maths worked out by hand?

The formula above, with small made-up numbers so you can check every step yourself - nothing here touches the live model below.

Take the sentence “cat sat mat”. In the real model, each token's Query, Key and Value come from its own vector multiplied by three separate learned weight matrices - one per role. To keep the arithmetic short, we'll skip that step and just suppose each token already has these toy vectors:

QueryKeyValue
cat(1, 0)(1, 0)(9, 1)
sat(0, 1)(0, 1)(2, 8)
mat(1, 1)(1, 0)(4, 4)

These three columns are simply picked for this example, not calculated from anything shown on this page - in a real model they'd fall out of multiplying each token's vector by the learned Q/K/V weight matrices mentioned above. Every token gets all three - a Query, a Key and a Value - it's not that "cat" only offers a Key while "sat" only asks a Query. Each token plays all three roles at once.

We'll trace what happens to “sat” below, purely because it makes a tidy example - there's nothing special about it, and it isn't processed first. Every token does this same three-step dance at the same time, each comparing its own Query against everyone's Keys, so "cat" and "mat" end up with their own new vectors too, worked out identically alongside “sat”.

Step 1 - “sat” builds its Query and compares it with every token's Key, using a dot product (multiply matching positions, add up):

sat·cat = (0×1 + 1×0) = 0  |  sat·sat = (0×0 + 1×1) = 1  |  sat·mat = (0×1 + 1×0) = 0

Step 2 - softmax turns those scores into weights that add up to 100%. It does this by exponentiating each score (eˣ - which stretches bigger scores further ahead of smaller ones), then dividing each by the total: e⁰=1, e¹≈2.72, e⁰=1, total≈4.72. So cat gets 1/4.72≈21%, sat gets 2.72/4.72≈58%, mat gets 1/4.72≈21%. Because “sat” only matches its own Key, softmax gives it most of the weight, but never all of it - it's a soft, not hard, choice, so cat and mat still get a small share.

Step 3 - blend the Values by those weights to get “sat”'s new, information-exchanged vector:

0.21×(9,1) + 0.58×(2,8) + 0.21×(4,4) ≈ (3.9, 5.7)

That result - (3.9, 5.7) - is “sat”'s new vector: mostly its own Value (2,8), since it attended to itself most, pulled a little toward “cat”'s Value (9,1) and “mat”'s Value (4,4), since they got a small share of the attention too. This new vector replaces “sat”'s old one and carries on into the rest of the block (and every block after it) - so by the time the model reaches the end, each token's vector has absorbed a bit of meaning from the tokens around it.

That's the entire mechanism in the formula above, worked out on a napkin. The live heatmap below does exactly this, at full scale, for your real sentence.

Technical layer

Each vector is projected to q=xW_Q, k=xW_K, v=xW_V. Weights are scaled dot-products then a row-wise softmax:

Attention(Q,K,V)=softmax(QKᵀ/√d_k)·V

Decoder-only (GPT-style) models add a causal mask: future positions are set to −∞ before softmax, so a token only attends to itself and earlier tokens - that's what makes left-to-right generation possible.

05

Many heads - several viewpoints at once

One attention pattern tracks one kind of relationship. So the model runs many heads in parallel, each learns different patterns of relationships - grammar, references, the previous token - then stitches them together.

🔬Think of it like this: a team of specialists reading the same sentence - a grammarian, a fact-checker, a continuity editor. Each highlights different links; the final read merges them all.
Technical layer

With h heads the model dimension splits; each head works in d_k=d/h dims with its own projections, then outputs concatenate through W_O:

MultiHead(X)=Concat(head_1…head_h)·W_O

GPT-2 small: 12 heads × 64 dims. Real heads with recognisable jobs have been found - “previous-token” heads, “induction” heads that copy patterns, and syntax-tracking heads.

Attention is only half a transformer block. (The many heads from the last section are this attention step - run several times in parallel, then merged into one - not a separate stage of their own.) After tokens exchange information, each one is processed alone by a small feed-forward network - a moment of private thinking where the model applies stored knowledge. Two stabilisers keep deep stacks trainable: residual connections (add to the signal rather than replace it) and normalisation (keep numbers healthy).

08

Next word - where generation happens

After the final layer, the model scores every token in its vocabulary for how well it fits next, turns those scores into probabilities (softmax), and picks one - usually with a little randomness. It adds that token and runs the whole thing again. That loop, one token at a time, is text generation.

🎲Think of it like this: a weighted raffle. Every candidate token gets tickets in proportion to how well it fits. The temperature dial sets fairness - low gives nearly all tickets to the favourite (predictable), high spreads them wide (creative, or chaotic).
Technical layer

The final vector is projected to logits z=W_U·h, then temperature-scaled before softmax:

p_i = exp(z_i/T) / Σ_j exp(z_j/T)

T→0 ≈ greedy argmax; T>1 flattens the distribution. Production adds top-k / nucleus (top-p) sampling.

↔ Is the forward pass really parallel? What changes at generation?

A single forward pass processes every token in the input simultaneously - all tokens exchange information through attention at the same time, not left to right. The sequential constraint only appears during generation: you cannot produce token 5 before token 4 exists, so each new token requires its own separate forward pass.

⚡ Doesn't reprocessing the whole context each time seem wasteful?

It would be - but there is a standard fix called the KV cache. During attention, every token produces a key vector and a value vector. For tokens already in the context, those vectors are identical to last time - the input tokens didn't change and the matrices didn't change, so the result must be the same. Rather than recomputing them, the system stores them after the first pass and reuses them on every subsequent step.

When a new token is added, only that token's K and V vectors need to be freshly computed. Attention then runs the new token's query against the full cached history of K and V vectors. All previous tokens' computations are skipped entirely.

What does still grow with context length is the attention step for the new token - comparing its query against every cached key. That cost grows linearly per token, and quadratically across a full generation, which is why very long contexts are expensive and why alternatives to full attention are an active research area.


Fixed at inference When you are using the model - this mode - the weights are completely frozen. Nothing you type changes them. Every request runs through the same fixed parameters the model finished training with; it is applying what it learned, not learning anything new from your input. Learning only ever happens during training.
Bottom line: a language model does one thing - predict the next token. Everything else emerges from repeating it.
08

Learning - how it got good in the first place

What training actually changes Training doesn't add or remove any matrices, and it doesn't change any shapes. It only changes the numbers inside. Before training starts, the entire structure already exists in memory - every matrix allocated to its fixed shape, filled with small random values. Then the process begins: run some text through the whole structure, compare what the model predicted against what actually came next, measure the error, and use that error signal to nudge every number in every matrix by a tiny amount in the direction that would have made the prediction slightly less wrong. Repeat that billions of times on billions of examples, and the random noise gradually resolves into something structured - the embedding table organises itself so that similar words end up near each other, the QKV matrices learn to recognise syntactic and semantic relationships, the feed-forward weights accumulate factual associations. The architecture never changes. The knowledge is entirely in the numbers.

Everything so far assumed the weights were already good. They aren't, to start with - they're random. Training is the loop that fixes that: show the model real text, ask it to predict the next token, measure how wrong it was (the loss), and nudge every weight a tiny bit to be less wrong next time. Repeat billions of times.

Objective: minimise cross-entropy of next-token prediction. Gradients of the loss w.r.t. every weight come from backpropagation; an optimiser (Adam/AdamW) takes a small step downhill: θ ← θ − η·∇L. That single objective, over trillions of tokens, is the source of everything the model can do.

09

From predictor to assistant - what comes after

Everything on this page so far produces a model that is very good at one thing: completing text. Given "The capital of France is", it will most likely say "Paris". But it has no particular reason to be helpful, accurate, or safe - it will just as readily complete "How do I..." by continuing the pattern of text it has seen. Turning that raw text-completer into an assistant like Claude, ChatGPT or Gemini takes further rounds of training on top. All of it still uses next-token prediction - what changes is the training signal.

📚Think of it like this: pre-training is like reading every book ever written, absorbing patterns and facts with no goal beyond predicting the next word. The stages below are an apprenticeship - first studying worked examples of ideal behaviour, then receiving feedback on your own attempts, until good behaviour is reliable.

Stage 1 - Instruction fine-tuning (SFT). The model is shown thousands of worked examples: a prompt on one side, a high-quality human-written response on the other. It is trained on those pairs in the usual way - predict the next token, measure the loss, nudge the weights. After enough examples the model learns the format: answer questions directly, follow instructions, stay on topic. The architecture has not changed at all; the weights have simply been steered toward a new target. A model fine-tuned this way is noticeably more useful than the raw pre-trained version - it stops trying to "continue" a question and starts trying to answer it.

But a model trained only on examples can still be unreliable in subtle ways: confidently wrong, inconsistently helpful, occasionally producing content nobody wanted. That's where the second stage comes in.

Stage 2 - RLHF (Reinforcement Learning from Human Feedback). Human raters are shown pairs of model responses to the same prompt and asked which they prefer. Those judgments are used to train a separate reward model - a network that learns to predict human preferences. The language model is then fine-tuned further using reinforcement learning: it generates responses, the reward model scores them, and the weights are nudged toward higher-scoring behaviour. Iterated many times, this shapes the model's tone, reliability and values.

🎯Think of it like this: imagine training a new colleague in two steps. First, show them a folder of ideal responses so they understand the format. Then have a manager give feedback - "that was better, that was worse" - until good behaviour is consistent. RLHF is that feedback loop, run millions of times, with the reward model standing in for the manager.

Stage 3 - Reasoning training. A newer stage, not yet in every model: more reinforcement learning, but this time rewarding the model for working through a problem step by step rather than just for the final answer - on tasks with a checkable right answer, like maths, code and logic. This is what powers "reasoning" models: given a hard problem, they generate a chain of intermediate reasoning steps as tokens before answering, which makes them noticeably better at multi-step problems - at the cost of extra time and tokens per answer.

Key insight At no point in any of these stages does the architecture change. There is no new component, no new type of layer. It is still the same transformer performing the same next-token prediction. What changes each time is the training signal - and that is enough to take a text-completer and give it a consistent personality, communication style, set of values, and - increasingly - the ability to reason through hard problems.
Technical layer

SFT is standard supervised learning on (prompt, completion) pairs, typically with a lower learning rate than pre-training to avoid overwriting too much. RLHF adds a second model: a reward model r(x,y) trained on human preference data using the Bradley-Terry objective. The language model is then optimised with PPO (Proximal Policy Optimisation) against r while a KL-divergence penalty keeps it close to the SFT checkpoint. A simpler offline variant, DPO (Direct Preference Optimisation), removes the RL step and frames preference learning as a classification problem directly on the language model - avoiding the need for a separate reward model. Most frontier labs now combine SFT, DPO or RLHF, and additional constitutional or rule-based filters. The model's weights after SFT serve as the starting point for RLHF; they are not reset between stages. Reasoning training differs from RLHF in one important way: because a maths or code answer can be checked automatically for correctness, this stage can reward the model directly on outcome, without needing a human-trained reward model - so it only works in these "verifiable" domains, not for open-ended writing or conversation.

⚠️What none of this fixes: a transformer only ever predicts text, so a few limits stay baked in whatever training it gets. It has no real-time knowledge - only what was in its training data, up to a cut-off date. It can hallucinate - produce fluent, confident text that's simply wrong, with no built-in way to tell the difference from a correct answer. It has no memory between separate conversations - each one starts fresh unless the history is resent. And it's not fully deterministic, even with randomness turned off. None of this is a bug to be trained away - it's a consequence of what the model is: a next-token predictor. Fixing it means building tools, memory and checks around the model, not just training it further.
Bottom line: a pre-trained transformer is a text completer. Instruction fine-tuning teaches it to answer rather than continue. RLHF shapes how it answers. Reasoning training teaches some models to work through hard problems step by step. Same architecture, same next-token prediction throughout - only the training signal changes.
✦

Where transformers came from

It helps to know why this design exists. Before 2017, language AI mostly used networks that read text one token at a time, in order (RNNs and LSTMs). Two problems dogged them: reading in sequence was slow to train, and they were forgetful - by the end of a long paragraph they'd lost track of the start.

In 2017 a team at Google published a paper with a bold title: “Attention Is All You Need.” Its key move was to drop the step-by-step reading entirely and let every token exchange information with every other token at once (the attention you explored above). That did two things: training became massively parallel - a perfect fit for modern hardware - and each token got a direct line to any other, no matter how far apart. The forgetting problem became much less severe.

That combination - attention plus the ability to scale - is what set off the current wave of AI. Take the same architecture, make it bigger, and train it on more text, and you get BERT, the GPT series, Claude, Gemini and almost every modern language model. They differ in size and training, but under the hood they're all transformers running the loop on this page.

The one-line history: old models read token-by-token and forgot; the transformer reads everything at once and exchanges information freely - and that changed everything.
